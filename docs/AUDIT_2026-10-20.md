# CulturePick 사전 점검 — 2026-10-20

> 후속 Docker 검증 완료: 기존 테스트 148개 통과, 별도 결함 재현 6개 모두 재현.
> 아래 최초 점검의 '미실행' 표기는 당시의 범위이며, 문서 끝의 후속 검증 표가 최신 상태다.

이 프로젝트는 공연 데이터를 수집해 검색·커뮤니티·개인화 추천을 제공한다.
공개 서비스에서 여러 사용자가 동시에 검색·로그인·추천을 요청하는 상황을 기준으로 점검했다.
대규모 트래픽은 가정하지 않았다. 운영 인프라의 별도 방어 장치는 확인하지 않았다.

## 범위와 검증

- 두 저장소의 구조, 주요 인증/공연/추천/커뮤니티/로그 경로, 설정, 배포 구성, 관련 테스트를 읽었다.
- Python 파일 120개의 AST 구문 분석 통과. 이는 테스트 통과나 런타임 호환성 확인이 아니다.
- AI 응답 검증 함수에 잘못된 JSON 구조 3개를 넣어 AttributeError/TypeError 발생을 격리 실행으로 확인했다.
- 학습 후보 갱신 함수를 mock ORM으로 실행해 수동 거절 상태가 자동 승인으로 바뀌고 과거 검수 정보가 유지되는 것을 확인했다.
- Git 추적 중인 sync_log.txt에서 service 쿼리의 키 형태 값 2건 발견. 값은 출력·재기록하지 않았다. 유효성은 미확인.
- 현재 Python 3.11에는 Django, DRF, nh3, pytest가 없고 Docker Linux 엔진 연결도 실패했다.
  의존성을 설치하거나 운영 서버를 호출하지 않았으므로 DB 통합 테스트·부하 테스트·실제 공격 재현은 수행하지 않았다.
- 아래 행 번호는 점검 시점 기준이다. P1은 우선 수정, P2는 후속 개선, P3는 정리 후보다.

## 우선 수정

### 1. [P1] Git 추적 로그에 KOPIS 키로 보이는 값이 남음

- 대상: `sync_log.txt:2557`, `sync_log.txt:12418`, `apps/performances/kopis/client.py:133`.
- 역할: KOPIS 요청 실패 로그를 저장한다.
- 문제: 요청의 service 쿼리 값이 로그에 포함되고 이 파일이 Git 추적 대상이다. client는 예외 문자열을 그대로 기록하므로 같은 일이 반복될 수 있다.
- 최소 조치: 실제 키인지 소유자가 확인하고 실제 자격증명이면 폐기/재발급한다. 로그 추적을 중단하고 요청 URL·예외에서 키를 마스킹한다. 과거 Git 이력 정리는 별도 범위로 결정한다.
- 미조치 영향: 저장소 접근자가 과거 키를 얻을 수 있다. 이번 점검에서는 키의 활성 여부와 원격 공개 여부를 확인하지 않았다.

### 2. [P1] 공개 게시글·댓글 API에서 이메일 노출

- 대상: `apps/community/serializers.py:19,117`, `apps/users/serializers.py:59`.
- 역할: 익명 사용자도 읽을 수 있는 게시글/댓글 응답을 만든다.
- 문제: author_email을 항상 반환하며 닉네임이 없으면 author_display_name에도 이메일이 들어간다. 이메일 필드만 제거해도 표시명 경로로 계속 노출된다.
- 최소 조치: 공개 표시명을 별도로 만들고 이메일을 제거 또는 비식별 값으로 치환한다. 기존 프론트의 author_email fallback을 고려해 비어 있지 않은 안전한 표시명을 유지한다.
- 미조치 영향: 공개 API를 순회해 사용자 이메일을 수집할 수 있다.

### 3. [P1] 로그인과 고비용·쓰기 API에 요청 제한이 없음

- 대상: `BE/settings/base.py:144`, `apps/users/views.py:85`, `apps/recommendations/views.py`, `apps/logs/views.py`, `apps/community/views.py:114`.
- 역할: 로그인, AI 호출, 로그 기록, 파일 업로드를 받는다.
- 문제: 복구 API에만 ScopedRateThrottle이 적용되어 있다. 로그인 반복 시도, 가입 후 AI 연속 호출·5MB 이미지 반복 업로드, 익명 로그 생성에 애플리케이션 제한이 없다. AI message에도 max_length가 없다.
- 최소 조치: 엔드포인트별 IP/계정 제한, 입력 길이와 업로드 누적량 제한을 둔다. 운영 프록시가 있다면 신뢰할 IP 전달 경로도 함께 검증한다.
- 미조치 영향: 계정 공격과 DB·저장 공간·추론 자원 고갈이 가능하다. 외부 WAF 존재 여부는 미확인이다.

### 4. [P1] 통신 보안이 일부 구간에서 비활성

- 대상: `BE/settings/base.py:230,233`, `apps/performances/tasks.py:105`, `apps/performances/kopis/client.py:15`, 프론트 `netlify.toml:3`.
- 역할: Redis/Valkey, KOPIS, Netlify→백엔드 간 통신을 설정한다.
- 문제: rediss 사용 시 인증서 검증을 CERT_NONE으로 끈다. KOPIS 기본 URL과 Netlify의 백엔드 목적지도 HTTP여서 해당 구간에서 API 키·인증/사용자 데이터의 전송 보호가 없다.
- 최소 조치: 인증서 검증을 켜고 신뢰할 CA를 설정한다. KOPIS HTTPS 지원과 AWS 인증서/도메인을 확인해 구간별 HTTPS를 적용한다.
- 미조치 영향: 경로를 가로채는 공격에 서버 신원과 데이터 기밀성을 보장할 수 없다. 실제 네트워크 침해를 확인한 것은 아니다.

### 5. [P1] 예상하지 못한 오류를 500 응답으로 바꾸면서 rollback을 놓침

- 대상: `common/exceptions.py:25`, `BE/settings/base.py:111`.
- 역할: 요청별 DB 트랜잭션 안에서 발생한 예외를 공통 오류 응답으로 변환한다.
- 문제: 기본 DRF 처리기가 처리하지 못한 Python 예외를 Response(500)으로 바꾸면서 rollback 표시를 하지 않는다. 추천 세션 생성 후 잘못된 AI 응답에서 AttributeError가 나면 세션 같은 선행 쓰기가 남을 수 있다.
- 최소 조치: 해당 분기에서 DRF set_rollback을 호출하거나 예외를 다시 올린다. DB 쓰기 후 일반 예외를 발생시켜 실제 rollback을 검증하는 테스트를 추가한다.
- 미조치 영향: 사용자는 실패를 받았는데 일부 데이터만 저장되는 상태가 발생한다.
- 근거: [DRF 3.15.2 공식 구현](https://github.com/encode/django-rest-framework/blob/3.15.2/rest_framework/views.py)은 처리된 APIException에 rollback을 표시하고, 나머지는 None을 반환한다. DB 통합 재현은 미실행이다.

### 6. [P1] AI 대기가 웹 서버와 DB 트랜잭션을 점유

- 대상: `docker-compose.yml:83`, `BE/settings/base.py:111`, `apps/recommendations/openai_client.py:88,140`, `apps/recommendations/services.py:610`.
- 역할: 하나의 HTTP 요청 안에서 후보 조회, AI 호출, 결과 저장을 수행한다.
- 문제: 운영 Compose는 Gunicorn worker 1개이며 별도 비동기 worker class가 없다. AI의 동기 응답을 기다리는 동안 일반 API 처리도 밀리고 요청 트랜잭션이 유지된다. AI 호출 timeout과 재시도 예산도 코드에 명시되어 있지 않다.
- 최소 조치: 우선 추론 시간 제한·재시도 예산을 정하고 외부 호출을 DB 트랜잭션 밖으로 분리한다. 메모리 여유에 맞춰 웹 처리 동시성을 조정하고, 비동기 작업 API는 실측상 필요할 때 도입한다.
- 미조치 영향: 느린 추천 하나가 검색·로그인 지연으로 번진다. 로컬 모델로 교체하면 더 두드러질 수 있다.

### 7. [P1] 동시 관심 등록 시 오류 또는 관심 수 불일치

- 대상: `apps/performances/views.py:305`.
- 역할: 관심/볼 예정 등록 여부를 바꾸고 zzim_count를 다시 센다.
- 문제: exists → create 사이에 잠금이 없다. 동일 사용자 동시 등록은 unique 제약 충돌로 실패할 수 있고, 다른 사용자 동시 등록은 각각 센 오래된 count를 덮어쓸 수 있다. atomic 블록만으로 이 순서가 직렬화되지는 않는다.
- 최소 조치: 관련 공연 행에 일관된 잠금을 잡고 상태 변경과 집계를 수행한다. PostgreSQL에서 병렬 요청 테스트로 확인한다.
- 미조치 영향: 중복 클릭·두 탭 사용에서도 500 또는 실제 관심 수와 다른 응답이 나올 수 있다. 기존 테스트는 순차 호출 중심이다.

### 8. [P1] 후속 피드백이 사람의 학습 데이터 검수 결과를 덮어씀

- 대상: `apps/recommendations/services.py:693,731`, `apps/recommendations/admin.py:87`, 학습 export 명령의 `_approved_queryset`.
- 역할: 피드백 점수에 따라 학습 후보를 갱신하고 검수된 후보를 내보낸다.
- 문제: 관리자가 거절한 후보도 후속 피드백에서 status/approved/chosen_output을 덮어쓴다. reviewed_by/reviewed_at은 유지되어 다시 승인된 항목이 새 검수 없이 export 조건을 통과할 수 있다. 피드백 중복 방지도 없어 같은 click을 반복해 점수를 올릴 수 있다.
- 최소 조치: 수동 검수 결정과 자동 점수를 분리하거나 검수된 상태의 자동 변경을 막는다. 검수 대상 내용이 달라지면 재검수가 필요하도록 하고 피드백 중복 정책을 정한다.
- 미조치 영향: 사람이 제외한 자료나 자동 생성 답변이 학습 데이터에 다시 들어간다. 로컬 파인튜닝 전에 해결해야 한다.
- 검증: 실제 함수를 mock ORM으로 실행했을 때 rejected → auto_approved, approved False → True, 과거 검수 정보 유지가 확인됐다. DB export까지의 통합 테스트는 미실행이다.

## 후속 개선

### 9. [P2] JSON 파싱 성공을 응답 구조 검증 성공으로 취급

- 대상: `apps/recommendations/openai_client.py:149`, `apps/recommendations/services.py:843`.
- 역할: AI 응답을 공연 카드로 변환한다.
- 문제: `[]`, `{"recommendations": null}`, `{"recommendations": [null]}`는 JSON 파싱은 되지만 AttributeError/TypeError가 난다. 호출부가 잡는 OpenAIRecommendationError가 아니어서 fallback으로 가지 않는다.
- 최소 조치: 반환 타입과 필드를 명시적으로 검증하고 잘못된 구조는 일관된 오류로 변환한다. 기존 3개 입력을 회귀 테스트로 사용한다.
- 미조치 영향: 구조화 출력 보장이 약한 로컬 모델 연결 시 대체 추천 대신 500이 발생한다.
- 검증: 위 3개 입력 모두 실제 검증 함수를 격리 실행해 예외 발생 확인.

### 10. [P2] 추천 후보별 DB 조회가 반복됨

- 대상: `apps/recommendations/services.py:292,380,563`, `apps/recommendations/views.py`, `apps/performances/serializers.py:90`.
- 역할: 최대 250개 후보의 특성 벡터를 확보하고 최종 공연 정보를 직렬화한다.
- 문제: 후보마다 PerformanceVector get_or_create를 호출하므로 캐시가 있어도 후보 수만큼 DB 조회가 생긴다. 최종 응답 queryset에는 price_options 및 사용자 actions prefetch가 없어 직렬화에서도 추가 조회가 발생한다.
- 최소 조치: 벡터를 일괄 조회하고 없는 항목만 생성한다. 최종 응답에서도 기존 공연 목록의 prefetch 패턴을 재사용한다.
- 미조치 영향: AI 호출 전후에 불필요한 DB 대기가 누적된다. 실제 소요 시간은 측정하지 않았다.

### 11. [P2] 프론트 요청 경로마다 토큰 만료 처리가 다름

- 대상: 프론트 `src/api/client.ts:57`, `src/api/recommendation.service.ts:63`, `src/api/mypage.service.ts`.
- 역할: API 호출 시 인증 토큰을 붙이고 만료를 처리한다.
- 문제: 공통 fetcher는 갱신을 시도하지만 AI 등 직접 fetch 경로는 401에서 바로 로그아웃 처리한다. 동시에 여러 fetcher가 401을 받으면 refresh가 중복 실행될 수 있으며 백엔드는 사용자당 refresh 값을 하나만 저장한다.
- 최소 조치: 프론트가 공통 요청·갱신 경로를 사용하고 동시 갱신 Promise를 공유하도록 요청한다. 백엔드 refresh 회전도 병렬 처리 테스트가 필요하다.
- 미조치 영향: 유효한 refresh가 있어도 AI 화면에서 세션이 끊기거나 동시 요청에서 갱신 충돌이 발생할 수 있다.

### 12. [P2] 채팅 화면이 이전 추천 맥락을 백엔드로 보내지 않음

- 대상: 프론트 `src/composables/useAiChat.ts:182`, `src/api/recommendation.service.ts:8`; 백엔드 `apps/recommendations/services.py:803`.
- 역할: “아까 것 말고 다른 공연” 같은 후속 추천을 처리한다.
- 문제: 백엔드는 session_id를 받지만 프론트는 message와 limit만 보낸다. 화면에 대화가 쌓여도 서버는 이전 후보를 알 수 없다.
- 최소 조치: 프론트가 응답의 session_id를 보관해 다음 요청에 넣고 대화 초기화 시 지우도록 요청한다.
- 미조치 영향: 후속 문장을 이해하지 못하거나 같은 공연을 다시 추천한다. 서버에서 무조건 마지막 세션을 추정하면 여러 탭의 대화가 섞이므로 권장하지 않는다.

### 13. [P2] 업로드한 이미지를 정리할 수명주기가 없음

- 대상: `apps/community/models.py:106`, `apps/community/serializers.py:191`, `apps/community/views.py:114`.
- 역할: 에디터에 넣을 이미지를 먼저 업로드한다.
- 문제: PostImage는 업로더만 기록하고 게시글과 연결되지 않는다. 글 작성 취소나 이미지 교체 후 저장소 파일을 정리하는 경로가 없다. 전체 검색에서도 파일 정리 signal/작업을 찾지 못했다.
- 최소 조치: 사용 중인 이미지 참조를 확인할 수 있도록 하고, 일정 기간 참조되지 않은 업로드를 삭제하는 최소 정리 절차를 만든다.
- 미조치 영향: 취소된 작성과 반복 업로드만으로도 파일이 계속 남는다. 현재 S3 저장량이나 실제 비용은 미확인이다.

### 14. [P2] 의존성 설치 결과와 테스트 실행을 재현하기 어려움

- 대상: `requirements/base.txt`, `requirements/production.txt`, `Dockerfile`.
- 역할: 배포 때 Python 패키지를 설치한다.

- 최소 조치: 검증된 환경을 constraints/lock으로 기록하고 주요 테스트를 자동 실행한다. PostgreSQL 동시성 테스트는 SQLite 테스트와 분리한다.
- 미조치 영향: 기기 이동이나 재배포 후 바뀐 동작을 코드 변경과 구분하기 어렵다. 설치된 정확한 버전·최신 CVE·지원 종료 여부는 이번에 판정하지 않았다.
