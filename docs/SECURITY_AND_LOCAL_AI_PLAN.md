# 키 교체 및 로컬 AI 준비 계획

2026-10-20 KST. 사용자 설명과 실제 확인 결과를 구분한다.

## 확인된 사항

- 사용자: Git 저장소는 공개. 실제 사용자를 유치해 서비스한 적은 없음.
- 사용자: AWS 무료 크레딧 소진으로 종료됐을 것으로 추정. 계정 플랜·현재 자원은 미확인.
- 사용자: 개인 PC에서 개발·시연하고 포트폴리오로 활용. 기존 AWS 구조 유지 불필요.
- 사용자: 보유 데이터 없음. 프론트 담당자에게 개선 후 필요한 변경 요청 가능.
- 로컬 Git에서 백엔드 37개, 프론트 54개 커밋에 도달 가능한 이력 검사.
  텍스트 blob 310개/455개를 키 형태·비밀값 할당·자격증명 URL 패턴으로 검색했다.
  이는 전용 전수 보안 감사가 아니며 원격 전용 브랜치, 삭제된 이력, GitHub 캐시/포크를 포함하지 않는다.
- 현재 sync_log.txt의 KOPIS 키 1종이 과거 .env.example에도 동일하게 존재함.
- 해당 키로 공식 HTTPS pblprfr API에 rows=1 요청 1회: HTTP 200, dbs 루트, 공연 1건 반환.
  키와 URL, 원문 응답은 출력·저장하지 않았다. 키가 현재 유효하다는 증거다.
- OpenAI 키 형태 검색 결과는 검토한 테스트 파일의 합성 예제였고,
  DB URL 검색 결과는 예제 값이었다. 다른 실제 비밀키가 노출되지 않았다고 보장할 수는 없다.

## 교체 대상

| 대상 | 현재 판정 | 필요한 조치 |
|---|---|---|
| KOPIS_API_KEY | 공개 이력 노출 + 현재 유효 확인 | 즉시 기존 키 폐기/재발급 요청. 재발급만으로 구 키가 무효화되는지 발급처에서 확인 |
| DJANGO_SECRET_KEY | 운영 사용값·노출 여부 미확인 | 새 로컬 환경은 새 난수 키 사용. 공개 예제값을 실제 환경에 썼거나 실제 값이 노출됐다면 교체. 기존 JWT/서명 링크 영향 확인 |
| OPENAI_API_SECRET_KEY / OPENAI_API_KEY | 실제 노출 증거 미확인 | 더 이상 쓰지 않는 키는 제공자 계정에서 폐기 권장. 사용 중이고 노출됐다면 교체 |
| GMS_API_KEY / GMS_KEY | 실제 노출 증거 미확인 | 학원 계정에서 미사용 키 폐기 또는 재발급 가능 여부 확인. 로컬 AI 준비에 필수 아님 |
| AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY | 실제 노출 증거 미확인 | IAM에서 이 프로젝트에 쓴 장기 키의 사용 현황 확인. 다른 프로젝트가 쓰지 않는 미사용 키는 비활성화 후 삭제 |
| DB_PASSWORD / DATABASE_URL 내 비밀번호 | 실제 운영값 미확인 | 기존 DB를 재사용하고 비밀번호 노출이 확인되면 DB 측 변경 후 앱 설정도 교체. 새 로컬 DB는 별도 자격증명 |
| GOOGLE_CLIENT_SECRET / NAVER_CLIENT_SECRET / EMAIL_HOST_PASSWORD | 실제 노출 증거 미확인 | 노출 또는 더 이상 사용하지 않는 자격증명에 대해 발급처 폐기/교체. 서버 설정만 지워도 발급처 키는 살아 있음 |

OAuth client ID, S3 버킷 이름, AWS 계정 번호는 비밀 인증키와 다르다.
공개되어 있다는 이유만으로 전부 재발급하거나 계정을 새로 만들 필요는 없다.
KOPIS 외에는 실제 운영 값의 공개 여부와 사용 상태를 먼저 확인한다.

## 환경변수 교체 절차

1. 발급처에서 노출된 기존 키를 무효화하고 새 키를 발급한다.
   현재는 서비스 연속성보다 공개 키 폐기를 우선한다. 다른 서비스가 함께 사용하는지도 확인한다.
2. 새 키는 백엔드 루트의 Git 제외 `.env`에 로컬 편집기로 입력한다.
   `.env.example`, README, 요청서, 채팅, 터미널 명령 인자에 실제 값을 넣지 않는다.
3. 로컬은 `.env.example`의 변수 이름만 참고한다. 기존 AWS 버킷/호스트는 그대로 복사하지 않는다.
   S3를 사용하지 않을 때 AWS_STORAGE_BUCKET_NAME, AWS_S3_CUSTOM_DOMAIN, AWS 장기 자격증명을 비운다.
4. KOPIS_API_KEY를 새 값으로 설정한다. AI를 외부 호출하지 않을 때 OpenAI/GMS 키 변수는 모두 비운다.
   별칭도 함께 확인한다: OPENAI_API_SECRET_KEY와 OPENAI_API_KEY, GMS_API_KEY와 GMS_KEY.
   로컬 provider 구현 전에는 임의로 AI_RECOMMENDATION_PROVIDER=local로 바꾸지 않는다.
5. 기존 프로세스/컨테이너를 재생성해 새 환경변수를 읽게 한다.
   현재 개발 Compose 사용 시 `docker compose -f docker-compose.local.yml up -d --force-recreate web celery-worker celery-beat`.
   이 명령은 실행 안내이며 이번 턴에 실행하지 않았다. DB/Redis 실행 및 정기 작업 설정을 먼저 확인한다.
   운영 AWS를 다시 쓸 때는 배포 플랫폼의 환경 속성을 교체하고 web/worker/beat 모두 반영됐는지 확인한다.
6. 서버에서 최소 조회로 새 키가 동작하는지 확인한다. 구 키 폐기는 발급처 상태로 우선 확인한다.
   DB/API 연결 URL을 포함한 오류 원문은 로그에 그대로 남기지 않는다.
7. `git check-ignore .env`, `git ls-files .env`, 커밋 예정 diff를 확인한다.
   이미 추적된 파일은 .gitignore에 추가하는 것만으로 보호되지 않는다.

변수 우선순위 주의:
- DB는 DATABASE_URL이 있으면 DB_*보다 우선한다.
- 로컬 Compose는 DATABASE_URL/Redis 연결을 컨테이너용 값으로 덮어쓴다.
- 키를 교체하려고 `.env`를 바꿔도 셸·Compose·배포 환경의 동일 변수가 남으면 예상과 다른 값이 사용될 수 있다.
- Django 키 교체 시 기존 사용자 로그인/비밀번호 재설정 링크가 무효화될 수 있다.

## 공개 Git 이력 처리

1. 키 폐기가 먼저다. 파일 삭제나 저장소 비공개 전환만으로 이미 유출된 키가 안전해지지 않는다.
2. SEC-01 구현에서 sync_log.txt 추적 중단·ignore·로그 마스킹을 함께 처리한다.
3. 필요하면 sync_log.txt와 과거 .env.example의 비밀값을 Git 이력에서도 제거한다.
   이력 재작성은 커밋 SHA를 바꾸므로 공유자와 협의하고 별도 작업으로 수행한다.
4. 협업자는 정리된 이력으로 다시 동기화해야 하며, 오래된 clone의 이력을 다시 push하면 안 된다.
5. GitHub secret scanning 알림과 접근 가능한 포크/캐시 대응 여부 확인.
   현재 이력 삭제·force push·키 폐기는 수행하지 않았다.

근거: https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository

## AWS 처리

사용자의 자동 종료 추정은 가능성이 있다.
AWS 공식 문서상 현재 Free plan은 크레딧 소진/기간 만료 시 종료되지만,
Paid plan은 크레딧 소진 뒤에도 계정이 닫히지 않고 비용이 발생할 수 있다.
먼저 Billing에서 플랜·청구 상태와 계정 종료 안내 메일을 확인한다.
계정 접근이 가능하면 사용했던 리전의 EB/EC2/RDS/ElastiCache/로드밸런서/S3/볼륨·스냅샷 잔존 여부를 확인한다.
이름만 보고 자원을 삭제하지 말고 테스트 계정/공연 데이터 등 보존할 자료가 있는지 확인한다.
데이터 확인만을 위해 유료 플랜으로 전환할 필요는 없다. 전환 전 비용과 복구 가치를 판단한다.

## 개발 환경 방향

- 노트북: 사용자 제공 Intel Core Ultra 5 228V, RAM 32GB, 내장 그래픽, SSD 약 900GB.
- 데스크톱: 사용자 제공 '4080TI', RAM 32GB, CPU 'intel 7 10900?'(미확인), SSD 여유 약 100GB.
- 정확한 GPU 모델과 VRAM을 확인하기 전에는 모델 크기·양자화·학습 배치 크기를 확정하지 않는다.
  데스크톱에서 `nvidia-smi --query-gpu=name,memory.total --format=csv` 결과면 충분하다.
- 현재 기기의 CIM 하드웨어 조회는 권한 제한으로 확인하지 못했다. 사용자 제공 사양을 실제 검증값으로 쓰지 않는다.
- 노트북은 백엔드 개발·테스트·데이터 검수 중심, 데스크톱은 GPU 추론·학습 실험 중심으로 제안.
- AWS 재구축은 지금 필수 아님. 개인 PC 시연에서 PostgreSQL과 필요한 Redis/Worker만 운영한다.
  정기 수집이 필요 없는 시연은 수동 동기화로 시작할 수 있다. Celery 제거를 지금 확정하지 않는다.
- 모델/학습 데이터는 별도 폴더에 두며 Git에 가중치·대용량 원본을 커밋하지 않는다.
  100GB 여유 공간에서 여러 모델·체크포인트를 동시에 보관하는 계획은 피한다.

## 데이터가 없는 상황의 해결책

공연 원천 데이터와 추천 학습 데이터는 별개다.

1. **공연 DB:** 새 KOPIS 키로 제한된 기간/장르부터 공연·공연장·가격 정보를 수집한다.
   먼저 100~300건 정도의 작은 스냅샷으로 파이프라인을 검증하는 방안을 제안한다.
   수집 시점과 출처를 기록하고, API 이용 조건·재배포·학습 사용 가능 범위를 확인한다.
   API 접근 권한이 포스터/소개문 등 모든 저작물의 학습·배포 허가를 뜻한다고 가정하지 않는다.
2. **평가셋 먼저:** 지역/장르/예산/동반자/재추천/조건 불충족 등 수십~100개 정도의 질문을 사람이 작성한다.
   정답을 하나의 공연으로 고정하기보다 만족해야 할 조건과 허용 후보, 설명 근거를 정의한다.
3. **학습셋:** 위 DB의 사실을 바탕으로 질문·후보·추천 이유를 작성한다.
   규칙 기반 초안이나 허용된 모델 생성 초안을 사람이 검수한다.
   개인정보가 없는 가상 취향 프로필은 사용할 수 있지만 실제 사용자 로그와 분리해 표시한다.
   처음에는 수백 건의 검수 샘플로 소규모 실험하며, 충분한 학습 효과를 보장하는 숫자로 취급하지 않는다.
4. **분리:** 비슷한 질문 표현·같은 공연/대화가 학습과 평가에 섞여 성능을 부풀리지 않도록 그룹 단위로 분리한다.
5. **비교:** 규칙 기반, 로컬 기본 모델, 파인튜닝 모델을 동일 평가셋에서 비교한다.
   조건 충족·사실성·후보 외 생성·JSON 유효성·응답 시간을 함께 측정한다.
6. **시연 설명:** 실제 사용자 데이터가 없으므로 사용자 만족도/행동 기반 추천 효과를 입증했다고 주장하지 않는다.
   대신 구조화된 요청 해석과 근거 기반 추천의 평가 결과를 포트폴리오에 제시한다.

공연의 최신 일정·가격을 모델에 암기시키기 위한 학습은 피한다.
기존처럼 DB에서 최신 후보를 선택하고, 모델에는 후보 안에서 추천하고 이유를 설명하는 능력을 학습시키는 방향을 권장한다.
